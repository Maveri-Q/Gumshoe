    How it works

    It's git bisect, the tool developers use to find a bad commit, with a browser test written from the bug report.

    1. Read the report

      The title and first post. Comments are left out, because they can hold the answer.

    2. Write one sentence

      Claude writes what should happen, as one sentence, plus the steps to get there. No code names, so the test still works on old versions.

    3. Test old versions

      Each version is built and opened in Chrome. Kane follows the steps, then a separate look says works or broken.

    4. Fix and keep

      A coding agent fixes it. Kane checks the fix with the same sentence. The sentence is saved as a Kane test.

    Cheap mode. Kane does the clicks once and saves a recording. Every older version replays it, and Kane's AI only looks at the end. The same search on report 9592 went from 531 credits and 59 minutes to 46 credits and 20 minutes, and found the same commit.

    How it avoids wrong answers

    A result only counts when three things agree: Kane's look, a second look that must not say both "works" and "broken", and a second reader that sees only the screenshot. Each version is tested twice, and both tests must agree. If they don't, the version is skipped, never guessed. 21 of 153 tests were thrown out this way.

    What it can't do yet

    • Old versions must still build. If one doesn't, it's skipped.
    • The report has to say what should happen.
    • Kane and the second reader can both misread a screen.
    • It finds where the behaviour changed. That isn't always the real cause.
    • 6 reports from 2 apps is a small sample.
    • Each app needs a short build file, written once by a person.
